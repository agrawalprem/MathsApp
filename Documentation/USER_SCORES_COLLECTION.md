# User Scores Collection Specification

## Collection: `user_scores`

This document defines the structure for the `user_scores` collection in Firestore, matching the Supabase table structure while including all fields needed for display in the Summary page and Teacher Dashboard.

## Document ID

- **Format**: `YYYYMMDDHHMISEC` (Year, Month, Day, Hour, Minute, Second) with collision handling
- **Generated by**: Current date/time formatted as `YYYYMMDDHHMISEC` (e.g., `"20260306065600"`)
- **Collision Handling**: 
  1. Generate base ID: Format current date/time as `YYYYMMDDHHMISEC`
  2. Try to create document with this ID
  3. If document already exists (collision), append `_1` and retry
  4. If still exists, try `_2`, `_3`, etc. until a unique ID is found
  5. Maximum retries: 100 (extremely rare edge case)
- **Purpose**: Human-readable, chronological ordering with guaranteed uniqueness
- **Example**: 
  - `"20260306065600"` - Document created on March 6, 2026 at 06:56:00
  - `"20260306065600_1"` - Second document if collision occurs at the same second
  - `"20260306065600_2"` - Third document if collision occurs at the same second

**Implementation Pseudocode**:
```javascript
function formatTimestampId(date) {
  const year = date.getFullYear();
  const month = String(date.getMonth() + 1).padStart(2, '0');
  const day = String(date.getDate()).padStart(2, '0');
  const hours = String(date.getHours()).padStart(2, '0');
  const minutes = String(date.getMinutes()).padStart(2, '0');
  const seconds = String(date.getSeconds()).padStart(2, '0');
  return `${year}${month}${day}${hours}${minutes}${seconds}`;
}

const now = new Date();
let baseId = formatTimestampId(now);
let docId = baseId;
let counter = 0;
let success = false;

while (!success && counter < 100) {
  const docRef = doc(db, 'user_scores', docId);
  const docSnapshot = await getDoc(docRef);
  
  if (!docSnapshot.exists()) {
    // Document doesn't exist, safe to create
    await setDoc(docRef, scoreDocument);
    success = true;
  } else {
    // Collision detected, try next ID
    counter++;
    docId = `${baseId}_${counter}`;
  }
}

if (!success) {
  throw new Error('Failed to generate unique document ID after 100 attempts');
}
```

| `user_id` | string | Yes | Firebase Auth UID (unique identifier for the authenticated user) |
| `user_code` | string | No | User code (e.g., "100001") - used for display and matching. **Not available for anonymous users** |
| ~~`email`~~ | ~~string~~ | ~~No~~ | ~~**REMOVED**: Email is only used for login/auth, not stored in user_scores collection~~ |

### User Profile Fields (Denormalized)

These fields are stored in `user_scores` for efficient querying without joins, matching what's displayed in the Teacher Dashboard.

**Note**: All user profile fields are **optional** and may be `null` for anonymous users who don't have a profile.

| Field Name | Type | Required | Description |
|------------|------|----------|-------------|
| `first_name` | string | No | Student's first name. **Null for anonymous users** |
| `last_name` | string | No | Student's last name. **Null for anonymous users** |
| `user_type` | string | No | User type (e.g., "Student", "Teacher", "Anonymous") |
| `gender` | string | No | Gender. **Null for anonymous users** |
| `date_of_birth` | string | No | Date of birth as string (YYYY-MM-DD format, e.g., "2010-05-15"). Uses **local timezone** date components to prevent timezone shifts. **Null for anonymous users** |
| `roll_number` | string | No | Roll number (displayed in Teacher Dashboard). **Null for anonymous users** |

### School and Class Fields

These fields are needed for filtering and display in the Teacher Dashboard.

| Field Name | Type | Required | Description |
|------------|------|----------|-------------|
| `school_id` | string | No | School identifier |
| `school_name` | string | No | School name (displayed in Teacher Dashboard) |
| `class` | string | No | Class number (e.g., "3", "4", "5") |
| `section` | string | No | Section letter (e.g., "A", "B", "C") |

**Note**: `class` and `section` are combined for display as "Class 3A" in the Teacher Dashboard.

### Score Fields

These fields match the Supabase `user_scores` table structure and are displayed in the Summary page.

| Field Name | Type | Required | Description |
|------------|------|----------|-------------|
| `operation` | string | Yes | Operation type: "addition", "subtraction", "multiplication", or "division" |
| `variant` | string | Yes | Variant identifier (e.g., "1A0", "2B", "3C9", "4A1") |
| `correct_count` | number | Yes | Number of correct answers (integer, default: 0) |
| `wrong_count` | number | Yes | Number of wrong answers (integer, default: 0) |
| `total_questions` | number | Yes | Total number of questions answered (integer, default: 0) |
| `total_time` | number | Yes | Total time taken in seconds (numeric 10,2 equivalent, default: 0) |
| `average_time` | number | No | Average time per correct answer in seconds (numeric 10,2 equivalent, default: 0) |
| `passed` | boolean | No | Whether the quiz was passed (default: false) |

### Metadata Fields

**None** - The document ID timestamp serves as the single source of truth for when the score was saved.

## Field Usage

### Summary Page Display

The Summary page displays:
- **User Info**: `first_name`, `last_name`, `class`, `section`, `roll_number` (in header)
- **Score Stats**: `correct_count`, `wrong_count`, `total_questions`, `total_time`, `average_time`, `passed`
- **Operation/Variant**: `operation`, `variant`

**Note**: Individual question results are **NOT** stored - they are only shown in the Summary page UI and then discarded.

### Teacher Dashboard Display

The Teacher Dashboard displays:
- **Fixed Columns**:
  - Student: `first_name` + `last_name`
  - Class: `class` + `section` (e.g., "3A")
  - Roll No.: `roll_number`
  - User Code: `user_code`
  - Date of Birth: `date_of_birth` (formatted as DD/MM/YYYY)

- **Variant Columns** (one per variant):
  - **Passed**: Shows `average_time` (e.g., "5.2s") if `passed === true`
  - **Failed**: Shows attempt count (count of records where `passed === false`) for that variant
  - **Active**: Shows different background color if student is currently working on this variant (from `active_sessions` collection, polled every 5-10 seconds)

- **Filtering**: Uses `school_id`, `school_name`, `class`, `section` for filtering students

**Note**: Active variant tracking uses `active_sessions` collection. Teacher Dashboard polls this collection periodically to detect which students are actively working on which variants.

## Query Patterns

### Common Queries

1. **Get all scores for a user**:
   ```javascript
   query(collection(db, 'user_scores'), where('user_id', '==', userId))
   ```

2. **Get scores for students in a school/class**:
   ```javascript
   query(
     collection(db, 'user_scores'),
     where('school_id', '==', schoolId),
     where('class', '==', classNum),
     where('section', '==', section)
   )
   ```

3. **Get passed scores for a variant**:
   ```javascript
   query(
     collection(db, 'user_scores'),
     where('user_id', '==', userId),
     where('operation', '==', operation),
     where('variant', '==', variant),
     where('passed', '==', true)
   )
   ```

## Indexes

Recommended Firestore composite indexes:

1. `user_id` + `operation` + `variant` + `passed`
2. `school_id` + `class` + `section`
3. `email` (for Teacher Dashboard queries)
4. `user_id` + Document ID (for chronological sorting - document ID is already chronological)

**Approach**: Uses `active_sessions` collection for tracking active quiz sessions. See **[ACTIVE_SESSIONS_COLLECTION.md](./ACTIVE_SESSIONS_COLLECTION.md)** for complete specification.

**Summary**:
- Collection: `active_sessions`
- Document ID: `user_id` (Firebase Auth UID)
- Fields: `user_id`, `operation`, `variant`, `last_question_no_completed`, `last_question_correct_wrong`, `total_questions`, `last_activity`
- Teacher Dashboard polls every 5-10 seconds to detect active sessions
- Matches Supabase structure exactly

## Notes

- **No Individual Question Results**: The `session_data` field from Supabase is not stored. Individual question results are only displayed in the Summary page UI and then discarded.

- **Denormalized Data**: User profile fields (`first_name`, `last_name`, `school_id`, `school_name`, `class`, `section`, etc.) are stored in each score document to avoid joins and improve query performance.

- **Document ID**: Uses timestamp string with collision handling for simple, chronological ordering. If multiple records are created at the exact same millisecond, a suffix (`_1`, `_2`, etc.) is appended to ensure uniqueness.

- **Active Sessions Collection**: Uses `active_sessions` collection. See **[ACTIVE_SESSIONS_COLLECTION.md](./ACTIVE_SESSIONS_COLLECTION.md)** for complete specification. Teacher Dashboard polls this collection every 5-10 seconds to detect active variants.

- **Anonymous Users**: All user profile fields (`user_code`, `email`, `first_name`, `last_name`, etc.) are optional and may be `null` for anonymous users who don't have a profile in `user_profiles`.

- **No Timestamp Fields**: Both `completed_at` and `created_at` are removed. The document ID timestamp serves as the single source of truth for when the score was saved.

## Firestore Listeners vs Polling Mechanisms

This section explains the two main approaches for getting real-time updates in the Teacher Dashboard, particularly relevant for tracking active variants and score updates.

### Firestore Listeners (Real-time Updates)

**What are Listeners?**
Firestore listeners are real-time subscriptions that automatically notify your application when data changes in the database. They use WebSocket connections to push updates immediately when documents are created, updated, or deleted.

**How They Work:**
1. **Subscribe**: Your app registers a listener on a collection or document
2. **Initial Data**: Listener immediately returns current data
3. **Real-time Updates**: Any changes trigger automatic callbacks
4. **Unsubscribe**: When done, remove the listener to stop receiving updates

**Example Code:**
```javascript
// Listen to all scores for a specific user
const unsubscribe = onSnapshot(
  query(collection(db, 'user_scores'), where('user_id', '==', userId)),
  (snapshot) => {
    snapshot.docChanges().forEach((change) => {
      if (change.type === 'added') {
        console.log('New score:', change.doc.data());
      }
      if (change.type === 'modified') {
        console.log('Updated score:', change.doc.data());
      }
      if (change.type === 'removed') {
        console.log('Deleted score:', change.doc.id);
      }
    });
  }
);

// Later, when done:
unsubscribe(); // Stop listening
```

**Listen to Multiple Students:**
```javascript
// Listen to user_profiles for active variant changes
const unsubscribe = onSnapshot(
  query(
    collection(db, 'user_profiles'),
    where('school_id', '==', schoolId),
    where('class', '==', classNum),
    where('section', '==', section)
  ),
  (snapshot) => {
    snapshot.docChanges().forEach((change) => {
      const student = change.doc.data();
      if (change.type === 'modified' && student.active_variant) {
        // Student started a new variant - update UI
        updateVariantCell(student.user_id, student.active_operation, student.active_variant, 'active');
      }
      if (change.type === 'modified' && !student.active_variant) {
        // Student completed variant - update UI
        updateVariantCell(student.user_id, null, null, 'completed');
      }
    });
  }
);
```

**Advantages:**
- ✅ **Real-time**: Updates appear instantly (no delay)
- ✅ **Efficient**: Only sends changes, not full data
- ✅ **Automatic**: No need to manually check for updates
- ✅ **Battery-friendly**: Server pushes updates only when needed
- ✅ **Scalable**: Handles many concurrent listeners efficiently

**Disadvantages:**
- ❌ **Connection overhead**: Maintains WebSocket connection
- ❌ **Complexity**: Need to handle connection errors, reconnection
- ❌ **Cost**: Firestore charges for document reads on each change
- ❌ **Memory**: Listeners consume memory and need cleanup

**Best For:**
- Real-time dashboards (like Teacher Dashboard)
- Active variant tracking
- Live score updates
- Collaborative features

### Polling Mechanism (Periodic Checks)

**What is Polling?**
Polling is a technique where your application periodically checks the database for changes by running queries at fixed intervals (e.g., every 5 seconds).

**How It Works:**
1. **Set Interval**: Use `setInterval()` to run a function periodically
2. **Query Database**: Execute a query to fetch current data
3. **Compare**: Compare with previous data to detect changes
4. **Update UI**: If changes detected, update the display
5. **Repeat**: Continue checking at regular intervals

**Example Code:**
```javascript
let previousScores = [];
let pollInterval = null;

function startPolling() {
  pollInterval = setInterval(async () => {
    try {
      // Query current scores
      const scoresSnapshot = await getDocs(
        query(collection(db, 'user_scores'), where('user_id', '==', userId))
      );
      
      const currentScores = scoresSnapshot.docs.map(doc => ({
        id: doc.id,
        ...doc.data()
      }));
      
      // Compare with previous
      const newScores = currentScores.filter(
        score => !previousScores.find(ps => ps.id === score.id)
      );
      
      if (newScores.length > 0) {
        console.log('New scores found:', newScores);
        updateUI(newScores);
      }
      
      previousScores = currentScores;
    } catch (error) {
      console.error('Polling error:', error);
    }
  }, 5000); // Poll every 5 seconds
}

function stopPolling() {
  if (pollInterval) {
    clearInterval(pollInterval);
    pollInterval = null;
  }
}
```

**Polling Active Variants:**
```javascript
let previousActiveVariants = new Map();

function pollActiveVariants() {
  setInterval(async () => {
    try {
      const studentsSnapshot = await getDocs(
        query(
          collection(db, 'user_profiles'),
          where('school_id', '==', schoolId),
          where('class', '==', classNum)
        )
      );
      
      const currentActive = new Map();
      studentsSnapshot.forEach(doc => {
        const student = doc.data();
        if (student.active_variant) {
          currentActive.set(student.user_id, {
            operation: student.active_operation,
            variant: student.active_variant
          });
        }
      });
      
      // Detect changes
      currentActive.forEach((active, userId) => {
        const previous = previousActiveVariants.get(userId);
        if (!previous || previous.variant !== active.variant) {
          // Active variant changed - update UI
          updateVariantCell(userId, active.operation, active.variant, 'active');
        }
      });
      
      // Detect completed (was active, now not)
      previousActiveVariants.forEach((active, userId) => {
        if (!currentActive.has(userId)) {
          // Student completed - update UI
          updateVariantCell(userId, null, null, 'completed');
        }
      });
      
      previousActiveVariants = currentActive;
    } catch (error) {
      console.error('Polling error:', error);
    }
  }, 5000); // Poll every 5 seconds
}
```

**Advantages:**
- ✅ **Simple**: Easy to implement and understand
- ✅ **Reliable**: Works even if WebSocket connections fail
- ✅ **Predictable**: Fixed interval, easy to debug
- ✅ **No connection overhead**: Uses regular HTTP requests
- ✅ **Control**: You decide when to check for updates

**Disadvantages:**
- ❌ **Delay**: Updates only appear at polling interval (e.g., 5 seconds)
- ❌ **Inefficient**: Fetches all data even if nothing changed
- ❌ **Battery drain**: Constant polling consumes resources
- ❌ **Cost**: Firestore charges for every query (even if no changes)
- ❌ **Scalability**: Doesn't scale well with many users

**Best For:**
- Simple dashboards with infrequent updates
- Background tasks
- Fallback when listeners aren't available
- One-time data fetches

### Comparison Table

| Aspect | Firestore Listeners | Polling |
|--------|---------------------|---------|
| **Update Speed** | Instant (real-time) | Delayed (polling interval) |
| **Network Efficiency** | Efficient (only changes) | Inefficient (full queries) |
| **Battery Usage** | Low (server pushes) | High (constant requests) |
| **Cost** | Pay per change | Pay per poll (even if no changes) |
| **Complexity** | Higher (connection management) | Lower (simple intervals) |
| **Reliability** | Depends on WebSocket | More reliable (HTTP fallback) |
| **Scalability** | Excellent | Poor (many intervals) |
| **Best Use Case** | Real-time dashboards | Simple, infrequent updates |

### Recommendation for Teacher Dashboard

**For Active Variant Tracking:**

**Approach: Polling `active_sessions` Collection (Selected)**
- Poll `active_sessions` collection every 5-10 seconds
- Query filtered by matching `user_id` with students in selected school/class/section
- Compare with previous state to detect changes
- Update UI when active sessions change (start/complete)
- **Pros**: Simple to implement, reliable, matches Supabase structure
- **Cons**: 5-10 second delay (acceptable), higher read costs (manageable)

**Why This Approach:**
- Simpler than listeners (no connection management)
- Acceptable delay is fine for this use case
- Matches existing Supabase structure (familiar)
- Separate collection keeps session state isolated
- Easy to understand and maintain

### Implementation Considerations

**For Listeners:**
1. **Cleanup**: Always unsubscribe listeners when component unmounts or page closes
2. **Error Handling**: Handle connection errors and implement reconnection logic
3. **Memory**: Limit number of concurrent listeners
4. **Cost**: Be aware of Firestore read costs for each change event

**For Polling:**
1. **Interval**: Choose appropriate interval (5-10 seconds for dashboards)
2. **Cleanup**: Clear intervals when not needed
3. **Efficiency**: Only poll when dashboard is visible (use Page Visibility API)
4. **Comparison**: Store previous state to detect actual changes

**Example Cleanup:**
```javascript
// Cleanup listeners
const listeners = [];

function addListener(query, callback) {
  const unsubscribe = onSnapshot(query, callback);
  listeners.push(unsubscribe);
  return unsubscribe;
}

function cleanupListeners() {
  listeners.forEach(unsubscribe => unsubscribe());
  listeners.length = 0;
}

// Cleanup polling
let pollInterval = null;

function startPolling() {
  pollInterval = setInterval(pollFunction, 5000);
}

function stopPolling() {
  if (pollInterval) {
    clearInterval(pollInterval);
    pollInterval = null;
  }
}

// Cleanup on page unload
window.addEventListener('beforeunload', () => {
  cleanupListeners();
  stopPolling();
});
```

### Summary

- **Firestore Listeners**: Best for real-time updates, efficient, but more complex. Recommended for Teacher Dashboard active variant tracking.

- **Polling**: Simpler to implement, but delayed updates and less efficient. Good as fallback or for simple use cases.

- **Recommendation**: Use Firestore listeners for the Teacher Dashboard to provide real-time updates when students start/complete variants, with polling as a fallback mechanism.
